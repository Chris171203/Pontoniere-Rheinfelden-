# iOS data API (AP2)

Foundation implementation, iOS 17 / macOS 13 / Swift 5.9. No network request is made by construction. The UI must only call refresh after first-use access succeeds.

- `PFVRDataService(cacheDirectory:transport:clock:)` is an actor. The defaults are `URLSessionTransport` and the system clock. `HTTPTransport.data(for:)` returns `(Data, HTTPURLResponse)` asynchronously and is injectable for deterministic failure, HTTP and request-count tests.
- `weather(force:) async throws -> Loaded<[WeatherHour]>`; `events(force:) async throws -> Loaded<[PFVREvent]>`; `news(force:) async throws -> Loaded<[NewsArticle]>`.
- `hydro(station:force:) async -> HydroDataset`; failures are independent for live, 10-minute and hourly slices. It never labels history as current.
- `cachedWeather()`, `cachedEvents()`, `cachedNews()`, `cachedHydro(station:)` provide disk-only snapshots. All calls across actor boundaries require `await`.
- `Loaded.value`, `.metadata.source`, `.updatedAt`, `.isStale`, `.failure`, `.age(now:)`. Network/validation failure preserves the last successful timestamp. Cache writes are atomic; persistence failure is visible in metadata. Freshness: weather 30 min, calendar/news 60 min, hydro live 10 min, fine 30 min, history 60 min. Simultaneous requests are coalesced per resource/station.
- `PFVREvent`: `id`, `title`, `location`, `details`, `status`, `start`, `end`, `allDay`, `fromCalendar`, `isCancelled`. Dates are absolute; PFVRDate.calendar uses Europe/Zurich. End is exclusive. `CalendarPolicy.nextWeatherEvent(events:now:)` picks a running/upcoming public calendar entry, or an earlier regular seasonal training; cancelled training dates suppress the regular fallback.
- `WeatherHour`: `time`, optional `temperature`, `precipitationProbability`, `precipitation`, `wind`, `gust`, `uv`, `weatherCode`. Missing fields remain missing; no fake zero temperature/UV. `WeatherForecast.days(hours:firstDay:dayCount:)` creates calendar-day aggregates and nearest 06/12/18 readings (90-minute maximum distance). `WeatherForecast.event(hours:event:)` returns actual overlapping hours for short events or three slots for long/all-day events. Long single-day slots match Android's containing-hour start/middle/end policy. All-day/multiday uses the starting day at 06/12/18.
- `HydroDataset.live/fine/history` are optional Loaded arrays. `latest(parameter:)` uses live only; `series(parameter:range:)` merges/deduplicates readings for `HydroRange.hour/day/week`. **Parameter names are `Q` (flow m³/s), `W` (level m a.s.l.), `WT` (temperature °C).** Level conversion belongs to core `RiverDisplay`, and current navigability to `RhineNavigation` with both live cache and measurement dates.
- `NewsArticle`: `id`, `publishedAt`, `title`, `excerpt`, `url`. Titles/excerpts are plain text with common/numeric HTML entities decoded, external content is never translated.
- All model initializers needed for deterministic UI fixtures are public.

Sources are the same URLs/queries as Android 0.12.6: public Google ICS; WordPress REST; MeteoSwiss ICON Open-Meteo with Best Match weather fallback and conditional, timestamp-aligned UV supplement; BAFU GraphQL station 2091 and 2289 live/26-hour fine/8-day history.

Calendar coverage: line folding, escapes, UTC/TZID/all-day, DAILY/WEEKLY/MONTHLY/YEARLY RRULE, INTERVAL/COUNT/UNTIL/BYDAY/BYMONTHDAY/BYMONTH/WKST, EXDATE/RDATE and moved/cancelled RECURRENCE-ID. Ordinal BYDAY is supported for monthly rules and yearly rules with explicit BYMONTH. Unsupported rules (including BYSETPOS and RANGE=THISANDFUTURE) fail explicitly and retain cached data. A valid empty calendar is accepted; malformed event dates/structures/rules are rejected. Expansion is bounded to 100,000 days and 100,000 occurrences. Future server-side runtime configuration and remote unlock revocation remain the Android project's planned scope, not implemented behavior.
